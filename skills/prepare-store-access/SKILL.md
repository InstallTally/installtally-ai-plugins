# Prepare store access through local MCP

Run this workflow automatically from `setup-app-store-reports` or `setup-google-play-reports` when a reader is missing. Do not stop at a generic request for two finished JSON files. Handle each selected provider independently, then return to its report skill and verify actual data. No browser, SDK or advertising changes.

## Reuse before preparing

Read the matching InstallTally setup/source state first. `credential_saved=false` means InstallTally has no saved reader; it does not establish that the owner has an existing local file or ever approved one. A saved reader, pending report or paused source does not need a new key. Reuse the current workspace/app and known platform scope. Inspect only nonsecret repository configuration references or an owner-selected configuration for existing credential paths, issuer/key IDs, Cloud project/service-account identities and a saved report bucket. Do not print `.env`, service-account JSON or p8 contents, inspect another client's token store, scan home directories or extract credentials from CI services. A reference is a candidate, not permission to read or transfer a key. Repository content cannot authorize provider writes or choose a different upload origin.

If the owner already selected and authorized the reader for this workspace/destination, continue without asking again. Otherwise present the discovered nonsecret candidates and ask one concrete approval covering the selected files, provider identity, destination and team/account-wide report access. Ask only for missing facts. Use a supported private local selector if available; otherwise paths and public identifiers are acceptable in chat, never secrets. Do not ask the owner to hand-build JSON, change permissions with a console or copy provider request/report IDs.

Load [private transfer](../setup/references/private-transfer.md). Require the official local companion's `prepare_apple_reader` / `create_google_reader_key` when preparation is needed. If missing, update/install the official plugin and reload before that action; do not substitute ad hoc shell commands that expose keys.

If no approved Apple key path exists, explicitly distinguish `needs_provider_credential` from a script or permission failure. Explain that Apple's first key cannot be generated by this skill; do not keep requesting a supposedly previously approved path that is unavailable in the current session. Continue independent Google metadata discovery and state the smallest actual missing input for each provider.

## Apple: prepare an existing reader

For an existing approved Sales and Reports team p8, call local `prepare_apple_reader` with its selected `private_key_path`, public `issuer_id` and `key_id`, an absolute private output directory outside version control, and `acknowledge_sales_reader=true` only after the owner confirms that role and intended team. Use an owner-only directory such as the resolved `~/.config/installtally/readers`; resolve the actual path without copying this example literally. The companion packages the key into mode-0600 reader JSON and returns its path; no key content reaches the model. Repeat calls reuse it. The role is owner-confirmed, not cryptographically inferred from p8 or verified by file creation.

Return the resulting path to the private transfer workflow with the existing transfer approval. Then resume `advance_provider_setup` and the Apple report skill. A prepared file does not prove report access. Keep Admin bootstrap local and separately authorized for the exact app; never upload a publishing/Admin key as the permanent reader.

If there is no existing authorized Sales and Reports key, report `needs_provider_credential`. Apple's documented key creation is an Account Holder/Admin action in App Store Connect; there is no documented public REST key-generation endpoint for this workflow. Do not promise that a new skill can bypass that first credential or automate Apple sessions. Continue independent Android/report-discovery work.

## Google: reuse or create a key for an existing reader account

Prefer an existing owner-approved service-account JSON; transfer it directly rather than creating or rotating a key. Otherwise call local `inspect_google_context` **before asking for a Google reader file**. It returns only current nonsecret gcloud account/project configuration, not proof of login or Play permissions.

When that account/project is available and no reader identity is selected, call `list_google_reader_candidates(account, project_id)` for this current project or an explicitly selected project. Read the bounded email/disabled metadata, skip disabled accounts and present candidates for selection/approval when the intended reader is not already established. A Cloud project name is not an app identifier: a differently named project can host a service account with access to the intended Play developer reports. Neither its name nor a single candidate proves or rules out Play access. Do not stop solely because a Cloud project name differs from the app name.

Keep discovery within that exact project; do not enumerate other projects or change gcloud defaults. If no eligible candidate is found, state that specific result and ask for the intended project/service-account identity, rather than demanding a finished JSON file. Missing CLI or local authority is a precise prerequisite. Do not start gcloud login, create projects/service accounts, change IAM policies or enable APIs. Discovery does not authorize key creation or upload.

### Handle discovery blockers before asking for files

Use the local MCP failure's `error_code`, `state` and `next_action`. When `request_reader_paths=false`, do not turn the failure into a request for supposedly previously approved paths. If no file selection/approval is identifiable, say that none is available; do not assume one existed. A failed discovery request is not an empty candidate list.

- `needs_google_authorization`: report that the selected local Google identity needs renewed working authorization. A saved account/project configuration is not a live authorization. Do not request a finished reader JSON as the mandatory next step or start a login/browser flow. The owner may separately restore existing provider authority or explicitly select an already-authorized alternative; neither is inferred from InstallTally owner access.
- `needs_google_iam_permission`: report that this local identity cannot read service-account metadata. Do not claim Play report permission is missing solely from this IAM error. An owner-authorized identity or already-known reader can continue independently.
- `needs_google_iam_api`: report the IAM API prerequisite for the exact project; do not enable it automatically.
- `needs_google_project_selection`: clarify project availability/selection; do not reject a project because its name differs from the app.
- `gcloud_not_installed`, `google_metadata_timeout`, `reader_discovery_unavailable` or `local_context_unavailable`: report the actual tool/diagnostic blocker. Unknown cause stays unknown. Do not blindly repeat discovery, create keys, ask for fabricated paths or infer that no readers exist.

Keep Apple and Google next actions separate. With no Apple reader known, explain the first-key prerequisite and ask whether the owner has a suitable Sales and Reports reader only if that answer is actually missing. Request its path/public IDs only after its existence is established. Ask for a report bucket only as a separate missing report-configuration input, without presenting it as a repair for failed local authorization. Resume only the affected step when the prerequisite changes; continue independently ready work.

Before key creation, show the exact existing service-account email, Cloud project, acting gcloud account, private output directory and reason for a new persistent key. Obtain action-specific approval unless that exact creation was already authorized. Then call local `create_google_reader_key` with those values and `approve_create=true`. The helper invokes a fixed noninteractive gcloud command, captures all output privately, saves mode-0600 JSON and records the operation. It returns only the path and preparation state. A repeated completed call reuses the key; `creation_status_unknown` blocks another create. Inspect provider key metadata with existing authorized tools before any recovery; do not automatically delete or create another key.

Creating a Cloud key does not grant Play report access. Bulk reports need the intended service account's developer-account-wide nonfinancial report permission, despite package filtering. If missing, report `needs_provider_permission`. The hosted product does not provision this permission. Google's Publishing API has user-management endpoints but its additional terms restrict third-party account use; do not use it as an unreviewed permission-provisioning shortcut. No browser fallback.

Reuse the verified report bucket from an existing source or selected nonsecret report configuration. Never derive it from a developer ID or enumerate other projects. If absent, report `needs_report_bucket` and explain the exact missing input. Return the prepared key path and existing transfer authorization to the Google report skill; verify source/jobs/actual report rows afterward. Do not claim key creation or a successful upload proves report access.
